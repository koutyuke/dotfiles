# 良いドキュメントを書く

ドキュメントを情報の保管場所ではなく、読者の認識と行動を揃えるインターフェースとして扱う。情報量ではなく、読者が短時間で全体像を理解し、正しく判断・行動できるかで品質を評価する。

## 1. 目的と読者を固定する

- 誰が、何のために、読後に何を判断または実行する文書かを特定する。
- 文書の種類を特定し、その目的を混ぜない。
  - README: 概要と利用開始
  - AGENTS.md: Agentが常に守る短い作業規則
  - ADR: 設計判断、理由、結果
  - Runbook: 運用・障害対応
  - Tutorial: 学習・作業順の案内
  - Reference: 正確な入出力や全項目の仕様
  - PR: 今回の変更、理由、検証、残リスク
- 対象読者、目的、期待する行動が不明で、合理的な仮定により結果が大きく変わる場合だけ確認する。

## 2. 根拠を確認する

- 新規作成では、正本となるコード、設定、仕様、既存文書を確認してから書く。
- 編集・更新では、対象箇所だけでなく関連する見出し、リンク、重複記述、正本を確認する。
- 事実、推論、提案、不明点を区別する。確認できない内容を補完しない。
- 「検討する」を「実行する」へ変えるなど、元情報の義務、禁止、推奨、可能性の強さを変えない。
- 読者が実行するために必要な情報源、判定者、権限、成功条件が不足している場合、曖昧な動詞や推論で隠さない。運用前に確定すべき未定義事項として、影響とともに文書の先頭で示す。
- 未定義事項により読者が一人で正しく行動できない場合、文書を実行可能または完成済みと表現しない。
- コードや設定から容易に確認できる事実を転載せず、判断理由、制約、境界、例外を優先する。

## 3. 最初に全体像を設計する

- 読者が全文を読まない前提で、最初の画面に結論、全体像、必要な行動のうち重要なものを置く。
- 詳細へ進む前に、数行の要約、入力と出力、手順一覧、責任範囲、または必要な図で認知の枠組みを与える。
- 一般に、結論 → 全体像 → 行動 → 制約・注意 → 詳細 → 補足の順で置く。文書の目的に合わない項目は省く。
- 手順書は、情報分類の美しさより実際の作業順を優先する。
- 条件分岐と分岐後の手順を近くに置く。別文書へ分ける場合も、分岐条件、移動先の目的、完了条件を分岐元に残す。

## 4. 必要な情報だけを書く

- 各記述について「削除すると読者の判断、行動、安全性、認識の一致が悪化するか」を確認する。悪化しない記述は削除する。
- 一般常識、自明な前置き、コードから明白な構造、本文の言い換え、装飾的なまとめを追加しない。
- 長い背景、全オプション、実装詳細は、現在の読者が正しく行動するために必要な場合だけ本文へ置く。
- 詳細を必要とする一部の読者向けには、正本となるReference、ADR、Runbook、コードなどへ案内する。
- 同じ情報を複数箇所へ複製しない。正本を一つ決める。ただし、短い結論やリンクを選ぶための条件まで別文書へ追い出さない。

## 5. 誤解なく行動できる形にする

- 「定義する」「作成する」「確認する」「対応する」「連絡する」「適切に」「必要に応じて」など、読者によって行動が変わる語をそのまま指示にしない。
- 解釈が分かれうる指示では、必要な範囲で主体、対象、手段、条件、入力、完了状態を示す。
- 元情報にない主体、決定権、連絡先、確認手段を推測で補わない。不足した要素を明示し、確認後に手順へ組み込む。
- 一文では一つの主要な指示を扱い、短く直接的に書く。
- 必須、禁止、原則、例外、参考を区別する。「必ず」や「禁止」は例外がない場合だけ使う。
- 非自明な禁止や制約には、理由、破った場合のリスク、安全な代替手段、例外条件のうち必要なものを添える。
- コマンドはコピーして実行できる形で示す。非自明なら実行場所、前提、入力、成功条件、失敗時の対応も示す。

## 6. 図とレイアウトを選ぶ

- 図は、文章より関係、順序、境界、分岐、状態遷移を速く正確に伝えられる場合に使う。
- 複数サービスのデータフロー、Trust Boundary、状態遷移、非同期の時系列、複雑な依存、障害時の経路には図を検討する。
- 数行の手順、単純な階層、本文を箱に入れ直しただけの内容、装飾目的には図を使わない。
- 図だけを唯一の情報源にしない。重要な結論、制約、例外を本文にも残す。
- 流れを上から下または左から右へ揃え、交差線、離れた凡例、過度に広い表、深すぎる階層を避ける。
- 色や線種だけに意味を依存させず、ラベルでも識別できるようにする。
- 頻繁に変わる詳細ではなく、安定した境界と関係を図示する。生成可能な図はコードや設定から生成する。

## 7. Markdownと強調を正しく使う

- 太字は重要な結論、警告、概念的な強調に使う。
- インラインコードは、コード識別子、コマンド、パス、設定値、環境変数、APIフィールド、文字どおり入力・選択する文字列に使う。一般語の強調には使わない。
- Markdownをファイルへ書く場合、文書全体を不要なコードフェンスで囲まない。
- Markdown内でフェンス付きコードブロックを例示する場合、埋め込む内容に含まれる最長の連続バッククォート数を確認し、外側にはそれより長い同数の開始・終了フェンスを使う。
- 見出し階層、リスト、表、リンク、コードフェンスが正しく表示されることを確認する。

## 8. 更新では現在の正しい状態へ再編集する

- 末尾への追記で済ませず、古い説明、重複、矛盾、不要になった例や図を削除・統合する。
- 通常の本文には「削除した」「以前は記載していた」など編集履歴を残さない。
- 履歴が必要なら、コミット、PR、CHANGELOG、ADR、Migration note、Release noteなど目的に合う場所へ記録する。
- 過去の挙動を知らないと事故が起きる場合は、編集履歴ではなく現在必要な互換性制約として書く。
- 追加文字数ではなく、更新後の文書全体の読みやすさと正確さを評価する。

## 9. 検証してから完了する

1. 正本と照合し、事実、リンク、パス、コマンド、コード例を確認する。
2. [評価基準](references/evaluation-rubric.md)を読み、必須条件をすべて満たすまで修正する。
3. 先頭から流し読みし、実際の作業順と視線移動を確認する。
4. 圧縮しても意味を失わない記述、重複、不要な前置き、編集履歴をもう一度削除する。
5. 図、表、コード例が本文だけより理解を改善しているか確認する。
6. 実施した検証、未確認事項、残る不確実性を報告する。

機械的に検証できる規則は、可能ならMarkdownリンター、リンク検査、文章校正、テスト、CIへ移す。文書では検査コマンド、適用範囲、例外条件だけを示す。
